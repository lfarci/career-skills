# Design Identity

Act as a candid designer: distinguish personal taste, strategic fit and craft. Guide choices in plain language; recommend with reasons.

## 1. Discover the need
- Interview before recommending: ask one high-level question at a time, use each answer to choose the next question, and probe vague answers or conflicting needs. Use grill-me if useful, without making it a dependency. Explain design choices in plain language rather than requiring design vocabulary.
- Start by explicitly asking what the user wants to create or improve and why. Wait for their answer before suggesting deliverables, styles, fonts or a direction. Example: "What would you like to create or improve, and what should it help you achieve?"
- Establish usage, goal and context: what the design represents, any relevant domain/industry, who will encounter it, where/how it will be used, and what it should make people feel, associate or remember. Ask only what is still missing; keep technical formats/sizes for after the high-level need is clear.
- Do not import a direction from memories, previous experiments, profession or existing website styling. A software engineer need not want a tech aesthetic; a previous geometric experiment is not a current brief. Reuse prior choices only when the user explicitly asks to continue them or supplies/references an existing brief, asset or design as the basis. A link to this skill is not a design reference. Even with references, clarify missing purpose and scope; ask which qualities to retain if unclear.
- Once the user has described the need, guide unresolved decisions with a few relevant examples and trade-offs. Discuss personality and style, then logo type only if a logo is needed. Offer recommendations grounded in their answers; do not lead with "continue the old direction or start fresh?"
- Agree on the requested deliverables and priorities: logo, typography/composition, palette, banners, icons or a broader system, as applicable. Confirm wording, constraints, freedom to change and required formats/sizes. Verify existing fonts/colours only when relevant to the agreed brief; do not treat them as mandatory.
- Ask where to store deliverables unless established. Save substantive questions, answers and clarifications in discovery.md; distinguish current answers, interpretations and historical references. Summarize the brief and agreed scope for correction before concepts.

## 2. Agree on concepts before drawing
- For logo work, read [logo design principles](references/logo-design-principles.md). Research a small relevant online reference set using its guidance; annotate what each teaches, link sources and avoid copying marks. If browsing is unavailable, state the gap.
- Derive two or three distinct concepts from the brief. Present them in words first: stable ID A/B/C, central idea, connection to the objective/audience, proposed visual construction and one trade-off. Distinguish an idea (connection, transformation, craft) from its style (geometric, organic). Do not assume technology or geometry.
- Recommend a direction and let the user select, combine or revise concepts. Wait for a concept choice before generating logo drafts or identity assets. Explicit concept choices in the current brief, or references the user asks to continue, satisfy this step; unrelated historical preferences do not.
- Record the selected concept and reasoning in discovery.md. If all fail, revisit the brief or concept rather than generating arbitrary logos.

## 3. Draft and compare
- Draft only agreed concepts and scoped deliverables. For typography/composition work, compare type hierarchy and layouts; for banners, compare compositions with the actual content and target crops. Skip logo-specific steps when no logo is requested. Default to two or three meaningfully different executions within the selected direction unless the user requests one; label concept/revision IDs clearly.
- Start logos in black and white: one clear idea, few deliberate elements, strong silhouette and useful negative space. Remove decorative detail; do not depend on colour, gradients, shadows or 3D effects for recognition.
- Compare at identical size/contrast; for logos, include required small sizes and reversed white-on-black. Inspect conceptual fit, distinctiveness and legibility before presenting. Simplify weak drafts rather than asking the user to filter obvious failures.
- Give concise rationale and trade-offs. Ask for feedback before refining; a preference does not approve future revisions. When a new logo is central to the scope, establish its direction before extending the system. Otherwise begin with the requested typography, composition or banners; keep applications comparable. Do not build full kits yet.
- Read [package structure](references/asset-structure.md) when saving. Keep options/revisions separate (A/v1, A/v2); preserve alternatives and feedback. Treat combined concepts as a new option.

## 4. Refine and deliver
- Change relevant variables; preserve accepted features. Compare existing typography before replacing it.
- Read [SVG guidance](references/svg-tooling.md) when constructing/exporting logos. Use image generation for raster drafts; use vector tools or direct SVG for vector masters. Render and inspect; label unverified work.
- Deliver identity.md, discovery.md (or canonical equivalents) and only scoped assets using the existing package structure. Document the applicable fonts, palette, logo and supporting visual rules with actual asset links. Produce only agreed asset types and exports; omit unused files and folders.
- Record the exact option/revision and obtain explicit approval before marking it approved. Keep alternatives available; do not publish beyond authorized scope.
- Let personal-brand own positioning and approved-kit inventory; audits assess implemented consistency. Load no external skill collection.

## Keep it lean
Reuse answers and update records incrementally. Read only stage-specific references; keep research bounded and explanations brief. Use text for concept decisions and visuals for draft comparisons. Generate full exports only for selected versions. Keep the existing file tree; create no extra process documents. Run relevant checks after changes.

## Done when
- Concepts were discussed before drafting; choices, feedback and revisions are traceable.
- Requested assets are saved and verified; a full engagement includes documented visual rules.
- Approval status, saved locations and outstanding limitations are explicit; no draft is presented as final.
